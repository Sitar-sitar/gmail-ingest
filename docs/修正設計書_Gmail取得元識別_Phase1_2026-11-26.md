## 1. 目的・背景

Phase 1 §1.1.1 で確認した Workspace AI Tools Addendum 2(d) により、OAuth のアクセスを取り消した場合は Gmail 由来の user data を保持できない。一方 `orders.csv` は Amazon 公式 CSV エクスポート由来の行と Gmail 由来の行が混在し、28 列のどこにも取得元を示す列がない。このため取り消し時に削除範囲を特定できず、F #27 の過去分一括削除（方式 A）も先行条件を満たせない。

**(a)「`Source` 列を追加」を採らない理由**は、列数が実装の複数箇所で固定されているためである（2026-11-26 に現行コードで確認）。

| 箇所 | 現状 |
|---|---|
| `amazon-tracker/tools/gmail-import-run.mjs` | `REQUIRED_COLUMNS = 28` を 5 箇所で参照（ヘッダー長の一致、重複なし集合のサイズ、不一致時の `throw`） |
| `gmail-ingest/lib/verify.mjs` の `parseOrders` | `header.length === 28` と**全行** `length === 28` を要求。違反は `VerificationError` → `permanent` となり、人の解除まで取り込みが止まる |
| `amazon-tracker/backups/orders/` | 42 世代すべて 28 列。`verifyAmazonApplied` はバックアップと適用後 CSV を比較するため、世代をまたいで幅が混在する |

列追加は Phase 1 §2.2 で OUT とした「既存の判定・検証ロジックを変更しない」領域に例外をもう 1 つ開ける変更になる。**なお §10-10 が (a) の難点に挙げた「既存 UI の CSV パースに衝突」は過大評価で、UI（`amazon-tracker/src/lib/useOrders.ts`）は列名でフィールドを引くため影響は小さい。** 実際の障壁は上表の 2 つである。

(b) は `orders.csv` の構造を触らず、識別キーの定義も既存の重複判定キー（`gmail-ingest/lib/verify.mjs` の `rowKeys()`）を再利用できる。

## 4. 設計方針

- `orders.csv` は触らない。識別情報は別ファイルに持つ。
- 対応表は**識別キーのハッシュだけ**を持ち、商品名・金額の平文を新たに増やさない。
- キーの定義は既存の重複判定キーに一致させ、二重定義しない。
- 取り込み時の追記を正本とし、過去分は遡及生成で一度だけ埋める。
- 遡及生成は機械的に導ける範囲に限る。導けない世代を自動で「公式由来」と決めつけず、人の判断として記録する。
- 取り消し時に識別できない行は、規約順守を優先して削除側に寄せる。ただし削除前にバックアップ世代と再取得の可用性を確認する。

## 5. 詳細仕様

### 5.1 決定記録 `gmail-ingest/state/origin-policy.json`

```
{
  "policy_id": "<本文の SHA-256>",
  "decided_at": "2026-11-26T..Z",
  "method": "mapping_table",
  "mapping_file": "amazon-tracker/data/gmail-origin.json",
  "key_spec": "rowkeys_exact_v1",
  "coverage": { "generated_at": "", "runs_covered": 0, "rows_covered": 0, "unresolved": [] }
}
```

- `policy_id` は `policy_id` を除いた本文の `JSON.stringify` の SHA-256（計画台帳の `planHash` と同方式）。
- 証跡台帳の `origin_policy_id` はこの値を書き写す（実装レビュー対応の修正設計 §5.1-1 の検証 3）。**このファイルが無い、または不一致なら過去分は 1 件も削除できない。**
- `state/` 配下なので Git 管理外。取り消し手順の完了後に削除する（§5.6）。

### 5.2 対応表 `amazon-tracker/data/gmail-origin.json`

```
{ "version": 1, "key_spec": "rowkeys_exact_v1", "updated_at": "", "entries": [ { "key_sha256": "", "count": 1 } ] }
```

- キーは `gmail-ingest/lib/verify.mjs` の `rowKeys(row).exact`（`Order ID` / 商品名 / 数量 / 金額 / 注文日の合成）。`key_sha256` はその UTF-8 文字列の SHA-256。**平文は保存しない。**
- `count` は同一キーを持つ行数（1 以上の整数）。キーの重複は不正とする。
- 書式検査: `key_sha256` が `^[a-f0-9]{64}$`、`count` が 1 以上の整数、`key_spec` が既知の値。違反は不正として扱う。
- `data/` 配下なので Git 管理外。これ自体が Gmail 由来の派生物なので、取り消し手順では使用後に削除する（§5.6）。

### 5.3 取り込み時の追記（`amazon-tracker/tools/gmail-import-run.mjs`）

Phase 1 §2.2 の**明示的な例外**として、既存 CLI にこの追記を加える（同ファイルは既に例外一覧に入っている）。

- 書き込み位置は既存のロック内。バックアップ → 一時 CSV 検証 → 本体置換が**成功した後**に行う。
- 加算するのは、その適用で**新たに `orders.csv` に存在するようになった行**のキーだけ。重複スキップ・除外・隔離の行は加えない。
- 旧サマリ置換で `orders.csv` から消えた行のキーは減算する（`count` を減らし、0 で項目を削除する）。
- 書き込みは一時ファイル＋`rename` の原子置換とし、直前の内容を `.bak` として 1 世代だけ残す。
- 書き込みに失敗した場合は非 0 終了とする。CSV は既に置換済みなので、復旧は §5.5 の修復手順に従う。
- 出力 JSON に `origin_mapping: { added, removed, total }` を加える。**キーもハッシュも出さない。**

### 5.4 ランナー側の独立照合（`gmail-ingest/lib/verify.mjs` / `jobs.mjs`）

- `executeAmazon` は適用前後の対応表を読み、`expectAmazonRows` が算出した期待（追記行・置換で消える行）と加減算が一致することを検証する。
- 不一致は `VerificationError` → `permanent` / `verify_mismatch` とし、確認済み期間を進めない（既存の照合失敗と同じ扱い）。
- 対応表が存在しない初回は空として扱い、加算分だけを検査する。破損（§5.2 の書式検査に違反）は照合失敗とする。
- 定常ログに出すのは件数だけ（Phase 1 §4.7）。

### 5.5 過去分の遡及生成（`amazon-tracker/tools/gmail-origin.mjs` 新規）

- 入力は `backups/orders/` の全 42 世代、現行 `orders.csv`、保持中 34 実行分の `candidates.json`、`gmail-import-rules.md` の変更履歴。**Gmail へは問い合わせない。**
- 手順: 世代を時刻順に並べ、隣接世代のキーの多重集合差で各適用が追加したキーを得る。最新世代と現行 CSV の差も同じ方法で取る。追加キーの和集合と現行 CSV のキーの積集合を対応表の候補とする。
- 相互照合: 各世代の追加件数が変更履歴の追記件数と一致すること、`candidates.json` がある世代（2026-05-17 以降）では候補のキーが追加キーを包含すること。**一致しない場合は報告して中断し、自動では採らない。**
- **被覆できない範囲**: 最古バックアップ（2026-05-05）より前の取り込み。変更履歴によれば 2026-04-26 の Type B 234 行は 2026-05-02 の公式デジタル CSV 一括置換（既存 `D01-` 242 件削除 → 1986 件追加）で `orders.csv` から消えており、残るのは 2026-05-02 の Gmail 差分 13 行（Type A 6 行 / Type B 7 行）である。この 13 行は機械的に特定できない。生成器は `coverage.unresolved` として報告し、**自動で判断しない**。
- 既定は dry-run（被覆報告のみ）。書き込みは `--apply` を付けた場合に限る。入力は読み取りのみで開く。
- **修復手順**: §5.3 の書き込みが途中で失敗した場合も同じ生成器を使う。該当実行の `candidates.json` と直前のバックアップ世代が残っている限り、その世代分を再計算して対応表へ入れ直せる。

### 5.6 権限取り消し時の使い方（Phase 1 §4.6-3 手順 6 の具体化）

- 対応表のキーと一致する現行 CSV の行を削除対象とする。**`count` を超える一致は削除しない**（過剰削除の防止）。
- 対応表に無い行は原則残す。`coverage.unresolved` がある場合は、その範囲（2026-05-02 の 13 行）を削除側に寄せるかを人が決め、判断を記録する。**既定は削除**（Addendum 2(d) の順守を優先）。
- 削除は Phase 1 §4.6-3 の処理順の「業務データ」段で行い、`dist/data/orders.csv` とバックアップも同じ手順の中で処理する。
- 手順の完了後に、対応表（`data/gmail-origin.json`）と決定記録（`state/origin-policy.json`）自体も削除する。

### 5.7 方式 A との接続（`origin_released`）

- 遡及生成が完了し、被覆報告が `unresolved` なし（または人の判断が記録済み）になった時点で、被覆された実行の中間成果物は取得元識別に不要になる。
- 証跡台帳の `origin_released` を true にできるのは、**被覆報告に載った実行ディレクトリの成果物に限る**。`unresolved` に関わる世代は false のまま保持する。
- 証跡台帳の `origin_policy_id` には §5.1 の `policy_id` を書き写す。

## 6. 既存機能の非破壊条件

- `orders.csv` の 28 列・列名・既存行を変更しない。`REQUIRED_COLUMNS` と `parseOrders` の 28 固定は維持する。
- 重複判定・除外・隔離・置換の判定ロジックを変更しない。対応表は結果の記録に限る。
- 対応表の不在は取り込みを止めない（初回は空から作る）。破損は §5.4 の照合失敗として扱う。
- 定常ログにキー・ハッシュ・パスを出さない。対応表と決定記録を Git に追加しない。

## 9. 受け入れ条件

- `orders.csv` の列数・列名・既存行が変わらず、既存の判定ロジックが変わらない。
- 取り込み 1 回ごとに、対応表の加減算が期待行集合と一致する。不一致では確認済み期間が進まない。
- 遡及生成が dry-run で被覆報告を出し、履歴件数と一致しない場合は書き込まない。
- `coverage.unresolved`（2026-05-02 の 13 行）が報告され、人の判断が記録されるまで、該当世代の `origin_released` を true にできない。
- 取り消し手順で、対応表のキーと一致する行だけが削除され、対応表と決定記録も削除される。
- 定常ログにキー・ハッシュ・パスが出ず、対応表と決定記録が Git に入らない。

## 10. リスク・ロールバック

- **バックアップを削除すると対応表を再生成できなくなる。** 対応表の再生成はバックアップ世代の差分に依存するため、Phase 1 §4.6-1 の「バックアップは Phase 1 では削除しない」を維持する。権限取り消し手順で削除する場合は、対応表の使用後に行う（§5.6 の順序）。
- 遡及生成の誤りは dry-run と履歴照合で検出する。書き込みは `--apply` のみ。
- 取り消しの過剰削除は `count` 上限と「対応表に無い行は残す」で制限する。実行前にバックアップ世代の存在を確認する。
- 対応表の変更は原子置換とし、直前の 1 世代を `.bak` として残す。異常時はそれに戻し、必要なら §5.5 で再生成する。

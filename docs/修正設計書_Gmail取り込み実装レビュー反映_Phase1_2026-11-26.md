## 1. 目的・背景

同じ週に一方の Amazon 取込が停止しても、処理可能な型の確認済み期間を進められるようにする。3リポジトリで複製した排他契約を自動で照合する。過去データは F #26 のユーザー判断に従って保持し、F #27 を再開する場合の判断と検証を先に定める。

## 2. スコープ

### 2.1 IN

- Amazon の型別スキップ、確定失敗の運用案内、共有ロックの契約テスト。
- 独立照合の回帰、移行台帳とカードのテスト入口の整理。
- F #27 で選択できる一括削除方式と、方式ごとの受入条件。

### 2.2 OUT

- 取得元識別策の選定・実装と本番データの処分は別承認とする。
- Gmail REST コアの共通化は Phase 2 の範囲とする。Phase 1 の非AI起動、CSV の28列、SQLite の構造、状態の schema v2、アプリごとの復元・排他を継承する。

## 4. 設計方針

確定済み期間は、その型の取得・照合・適用確認まで成功した場合に限って進める。CSV は1つのロックの下で読み取りから検証まで一貫させる。データの棚卸し、削除対象の適格性、人の承認はそれぞれ独立した条件として記録する。

## 5. 詳細仕様

### 5.1 F #27 の再開条件と一括削除方式（P1-01）

現在は元データを保持し、`state/cleanup-enabled` と `state/auto-cleanup-enabled` を未配置とする。再開には次の順序で確認が必要となる。

1. Phase 1 §10-10 の取得元識別策を決める。遡及照合に必要な本文・候補・payload と、その方法で必要な公式入力を特定し、読み取り可能なことを確認する。再構築を選んだ場合は、公式 CSV を使った再構築を隔離環境で検証する。必要な資料を確認できなければ保留を継続する。
2. ユーザーが下記の A/B を選ぶ。選択をこの節と Phase 1 の #27 に記録し、選択した方式の隔離受入を終える。
3. 本番操作には別途、対象集合・保全対象・影響を示して承認を得る。定常削除の有効化は、一括方式と必要資料の保全が確定した後に個別に判断する。

| 方式 | 実装・運用契約 |
|---|---|
| A。過去分の一括削除を設ける | `lib/cleanup.mjs` の一括計画に旧実行の証跡を照合した項目を明示的に追加する。元成果物と当時の適用成功を対応付けられる証跡と、取得元識別に不要になった根拠を項目ごとに求める。証跡が不足する項目、未解決隔離、解析失敗、保全対象は保持する。旧実行の証跡は非公開の計画内で扱い、`verified-artifacts.json` を遡及書換えしない。計画は対象と根拠の版を固定し、承認を `plan_id` と対象のルート・種別・パス・サイズ・mtime・SHA-256 に結び付ける。実行直前に同一性と対象制限を再検証し、差し替えは保持する。一括承認は一回で消費し、中断後の再開には再棚卸しと新規承認を求める。定常削除はランナーの照合済み台帳を引き続き使用する。証跡の入力形式・供給元はこの案を選んだ時点で設計に確定する。 |
| B。過去分の一括削除を取り下げる | 過去分の棚卸しを残し、README・Phase 1 §2.1・§4.6・#27・受入条件から過去分を一括削除できるという運用を外す。旧成果物は保持し、必要な個別処分は資料の保全と根拠を確認して別途判断する。Phase 1 §4.6-3 の権限取り消し手順は独立して扱う。 |

### 5.2 Amazon の確定失敗の解除と型別スキップ（P2-01）

- 短期は `README.md` の失敗復旧手順に Phase 1 §4.5-2 を転記する。両型に未承認の失敗 ID が残る場合は、原因を確認して型ごとの ID で `node run.mjs --clear-failure <failure_id> --job amazon` を実行する。ID はその型と失敗区間だけを承認し、解除操作は確認済み期間を変更しない。
- 恒久対応では `run.mjs` / `jobs.mjs` が通常実行・欠落回収で実際に範囲を持ち、承認済みまたはブロックされていない型を選ぶ。この集合を `amazon-tracker/tools/gmail-fetch-local.mjs` の `--types <カンマ区切り>` に `type_a`・`type_b` の値で渡す。省略時は従来どおり両型。未知の型・空集合・重複の指定は Gmail アクセス前に拒否する。検索専用モードは既存の両型検索契約を継承する。
- 選ばれなかった型は検索・本文取得・候補生成・適用を行わない。選択型の検索 ID・元本文・金額・適用結果だけを独立検証し、既存 CSV に対する意図せぬ変更も検証する。`rangeStart()` の当日フォールバックは選択型を決める処理から外す。
- スキップした型の状態・確認済み期間・承認は保持する。選択型に限り実行開始時にその失敗の承認を一回消費し、適用確認に成功した型の期間を確定する。適用前の確定失敗を型に帰属できる場合は適用を見送り、当該型に失敗を記録する。他の選択型は未適用として記録し、確認済み期間を据え置く。共通 CSV の適用・事後検証など帰属不能な確定失敗は参加した全型に記録する。
- 実行対象のすべてが未承認でスキップされた場合のみ終了コード5。結果の集約は既存の終了コード契約を継承し、予定していた型をスキップした週次枠は未完了のまま保持する。

### 5.3 共有ロックの契約テスト（P2-02）

`lib/lock.mjs`、`amazon-tracker/tools/gmail-import-run.mjs`、`credit-card-tracker/tools/gmail-import-apply.mjs` の各リポジトリに、ローカルの自ファイルだけを読む契約テストを追加する。改行を LF に正規化し、`// Keep the on-disk contract identical in direct import entry points.` から `joinImportLock` の末尾までを抽出する。抽出の終端はランナーがファイル末尾、両アプリは後続の `const ROOT = process.cwd();` の直前とし、末尾の空行を一つの改行へ正規化する。開始・終端の欠落や重複はテスト失敗とする。

前提コミットで実測した UTF-8 の正規化後 SHA-256 は `992f0a21709e1bee3348f442faf7861072788800ddbffa94ef50ba3e3707500f`。3つのテストが同じ固定値を参照する。契約を更新する場合は3リポジトリの対象コミットと期待値を同じリリース作業で突き合わせ、片側だけを本番配備しない。ハッシュ比較に加え、既存の排他・所有者・回収の動作試験を通す。

### 5.4 Amazon の独立照合の保守（P3-01）

`gmail-import-rules.md` に、Gmail 書式変更時は Amazon のパーサと `lib/verify.mjs` の両方を確認する運用を記載する。照合は引き続き元の本文から再計算する。Type A の複数商品・数量・割引・注文総額、Type B の明細と予約除外について、同じ合成メールでパーサと照合器を通す。意図的に改変した候補を照合器が拒否する試験も加える。

### 5.5 台帳とテスト入口（P3-04）

- Amazon の旧 Codex Automation 記録は履歴として評価する。ローカル追記を保持したまま、旧記録の日付と現行の確認済み期間が別の意味を持つことを示し、取り込み状態は `gmail-ingest/state/last-run.json` を参照する。履歴の整理方法は所有者の判断を記録する。
- 親 `PROJECT_OVERVIEW.md` の初期化メモは、初回コミットと `origin` 設定済みの事実に合わせる。本番切替状況は同台帳の現行欄を参照する。
- カードの `package.json` に `npm test` を追加し、既存の `test:parser`、`test:import`、`test:automation` を順に実行して、1系統でも失敗すれば非ゼロで終了する。既存の個別入口は利用できる。Phase 1 §8.2 の3コマンドは集約入口が入るまで現行の実行手順とする。

## 6. 既存機能の非破壊条件

- 週次タスク、手動実行、ロールバックで同じ認証・出力先照合を行う。カードは provider 単位の成功確定を継続する。
- Amazon 直接 CLI の既存呼び出しと CSV/SQLite の既存行を維持する。既存 schema v2 と `partial` は引き続き読める。
- メール本文、業務上の識別子、個別ファイルパスは定常ログに出さない。旧手動 AI 入口は診断専用のままとする。

## 9. 受け入れ条件

- ブロック中の型には Gmail 検索も書込みも発生せず、実行可能な型の期間だけが適用確認後に進む。両型ブロック時は Amazon の子 CLI が起動しない。
- 同版の3コピーで排他テストが成立し、ロック実装の片側変更を配備前に検出できる。
- F #27 の保留中は両フラグが未配置で、元データの削除件数は0。再開する場合は選んだ方式の受入を満たし、対象と保全の根拠を実行前に確認できる。

## 10. リスク・ロールバック

型別変更の回帰時は、先に週次タスクを停止して実行中の書込みが終わったことを確認し、互換性を確認した3リポジトリの検証済み版へまとめて戻す。期間状態や CSV・SQLite の復元が必要な場合は Phase 1 §7-1 の世代単位の手順に従う。清掃の異常時は以後の承認・定常実行を停止し、削除済み項目の有無と保全資料を個別に照合する。

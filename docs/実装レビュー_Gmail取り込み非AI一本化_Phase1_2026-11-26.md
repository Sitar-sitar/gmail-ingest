## 設計要件の充足（主要点）

- **R3-02（承認の2系統）**　`autoCleanup` は `state/auto-cleanup-enabled` の存在を必須とし、`executeCleanup` は `cleanup-enabled` と計画台帳だけを消費して定常フラグに触れない。一括削除の承認消費で週次の自動削除が止まる経路はない。
- **R3-03（確定失敗の停止粒度）**　カードは provider 単位のジョブとして列挙され、1社が未承認 `permanent` でも他の2社と Amazon は通常実行される。全対象がスキップで新規実行0件のときだけ終了コード5。専用テストで担保されている。
- **R2-01（金額照合）**　Type A は「1注文の総額が各行の `Total Amount` に重複して入る」実装どおりに行ごとに照合し、`Shipment Item Subtotal === Unit Price × Original Quantity` を併せて確認する。Type B は `Σ Total Amount === 総計`、`Σ Total Discounts === 割引` で照合する。初回反映時に正常系を永久失敗させた式は再発していない。
- **R2-02（受信期間と利用日下限の分離）**　カードは検索クエリの `newer:` / `older:` を JST 日境界の秒指定（`after:` / `before:`）へ書き換え、45日＋1秒の上限を超える範囲を拒否する。利用日下限は `--business-from` として別引数で渡り、ランナー側も `ingest_bounds` を突き合わせる。太平洋時間境界による取りこぼしの経路は閉じている。
- **R2-07（復元セット）**　`VACUUM INTO` で SQLite の整合コピーを作り、両アプリのロック保持を必須条件とし、`PRAGMA quick_check`・テーブル件数・CSV 行数・状態スキーマまで照合して `verified` を立てる。移行前の人間向け記録4件も世代に含められる。
- **R2-15（診断欄）**　`import_runs.note` は `success` / `parse` / `apply_error` の分類コードのみになり、例外本文とログパスは入らない。人間向けログからも DB の絶対パス行が削除されている。
- **認証の一本化**　`amazon-tracker` のリポジトリ間自動コピー経路は削除済み。`--check-auth` は正規化アドレスの SHA-256 のみを返し、値そのものは出さない。ランナーは状態に記録した識別子と一致しない限り何も実行しない。
- **排他**　書込み対象側のロックを子CLIにも置き、`GMAIL_INGEST_LOCK_TOKEN` で引継ぐ。子ツリーの停止を確認できない場合は `pending_human_review` を立てて以後の自動実行を終了コード3で止める。
- **切替順**　`register-task.ps1` は `state/cutover.json` の `first-run-verified` がない限り本番タスクを登録しない（R2-06 の順序が仕組みで担保されている）。
- **AI経路の診断専用化**　親リポ `.claude/CLAUDE.md` §7、`.claude/commands/amazon-import.md`、`AGENTS.md` §6.4、Codex スキルがいずれも読み取り診断に限定され、取得・適用・状態更新・失敗解除・削除を起動しないと明記されている。

## 指摘

### P1-01［P1］F #27 を再開しても過去分は1件も削除できない

**該当**　`lib/cleanup.mjs`（`createCleanupPlan` の `eligible` 判定、`executeCleanup` の継続条件）、設計書 §2.1 IN・§4.6-1 末尾・§4.6-2。

**根拠**　`createCleanupPlan` は各対象の `eligible` を「`verified`（= `state/verified-artifacts.json` にランナー自身の生成記録がある）かつ未解決隔離でなく保持期限超過」で決める。`executeCleanup` は `eligible` 以外を一切削除しない。したがって**ランナーの記録がない過去分は構造的に削除対象にならない**。合成データで確認した結果は、過去分4件（Amazon 本文 JSONL・候補 JSON、カード本文 JSONL・payload JSON、いずれも mtime 180日前）に対し計画の検出4件・`eligible` 0件、承認後の一括削除 0件、`auto-cleanup-enabled` 配置後の定常削除も 0件だった。種別判定そのものは過去分の実パス（年月別ディレクトリ配下の `messages.jsonl`、`data/` 直下の `import-<provider>-*.json`）を正しく拾えているため、検出はできて削除だけができない状態である。

**影響**　§2.1 IN が成果物として掲げる「既存の残存中間データの一括削除」（Amazon 66ファイル 8.0MB / カード 190ファイル 32.4MB ほか）が、実装のままでは実行できない。現在は F #26 のユーザー判断で元データを保持しているため実害はないが、**保留を解除する時点で手順が空振りする**。

**原因の所在**　実装の判断ミスではなく設計内の衝突である。§2.1 IN と §4.6-2 は過去分の一括削除を成果物とする一方、§4.6-1 末尾と §4.6-2 手順6は「適用成功を証明できない過去分は保留する」と定めている。過去分には定義上ランナーの成功記録がないため、後者を厳格に実装すると前者が消える。

**推奨対応**　どちらを正本にするかをユーザーが決め、設計書を直してから実装する。

- (a) 過去分を削除対象にする場合: 計画の未検証エントリに対する**人の明示承認の経路**を設計に追加する（例: `--enable-cleanup --plan-id <id> --include-unverified` を別フラグとして定義し、承認を計画の版と対象の同一性に束縛したまま、過去分だけを対象に含める）。§4.6-1 末尾・§4.6-2 手順6の「保留」と両立させる条件（種別・経過日数・`parse-failures.json` 不在・未解決隔離除外など）を明文化する。
- (b) 過去分を一括削除の対象から外す場合: §2.1 IN と §4.6-2 の見出しから一括削除を撤回し、過去分は §4.6-3（権限取り消し手順）または人の手作業で扱うと明記する。`--cleanup-plan` は検出と一覧化までを担うと位置づける。

**2026-11-26 決定**　ユーザー判断により **(a)** を採用した。証跡の入力形式・供給元・検証・承認範囲・消費は [レビュー対応の修正設計](修正設計書_Gmail取り込み実装レビュー反映_Phase1_2026-11-26.md) §5.1-1 に確定し、Phase 1 設計書の §2.1 IN・§4.6-2・§4.6-2a・§6 #27・§9 を同期した。実装は §10-10 の取得元識別策の決定後に行う。

### P2-01［P2］Amazon の確定失敗は Type A/B 双方を止め、解除も2件必要

**該当**　`run.mjs`（`available` の絞り込み）、`jobs.mjs`（`listJobs` の Amazon ジョブ定義）、`README.md`、設計書 §4.4・§4.5-2。

**根拠**　カードは provider ごとに1ジョブとして列挙されるが、Amazon は Type A と Type B を1ジョブの2対象として持ち、`available` の判定が「ブロック対象が0件であること」のため**どちらか一方が未承認 `permanent` ならジョブ全体がスキップされる**。また `run.mjs` は Amazon の結果を両対象に同一記録するため、1回の確定失敗で `failure_id` が2件生成される。合成データで、CSV 検証失敗を1回起こしたのち `type_a` の `failure_id` だけを解除して再実行したところ、Amazon は1ステップも起動せず終了コード5、確認済み期間も据え置きだった。両方を解除した再実行で正常に成功し期間が進んだ。

**影響**　設計書 §4.5-2 の「未承認の `permanent` が残っている対象は、その対象だけをスキップする」と §4.4 の「粒度は Amazon が Type A / Type B 別」に対する逸脱。Type A の失敗で Kindle（Type B）の取り込みも止まる。確認済み期間は進まないので取り込み漏れにはならないが、復旧が遅れる。加えて `README.md` の案内は `--clear-failure <failure_id> --job <job>` を1回実行する形になっており、**2件必要であることがどこにも書かれていない**。片方だけ解除した状態ではスキップのログに解除済み対象が現れないため、運用者が原因を追いにくい。

**推奨対応**　短期は `README.md` と設計書に「Amazon の確定失敗は Type A / Type B の2件を解除する」と明記する。恒久対応として、ブロック中の型の範囲を `null` にして実行する形に変えれば型別スキップは実装可能（`executeAmazon` の `rangeStart()` は既に範囲なしの型を許容し、記録も範囲のある型だけに限っている）。

### P2-02［P2］ロック実装が3ファイルに複製されている

**該当**　`lib/lock.mjs`、`amazon-tracker/tools/gmail-import-run.mjs`、`credit-card-tracker/tools/gmail-import-apply.mjs`（`credit-card-tracker/tools/gmail-raw-payload.mjs` は apply から取り込む形で重複なし）。

**根拠**　3ファイルの該当ブロックは現時点でバイト単位まで同一（各5045バイト、同一ハッシュ）。独立リポジトリ間でモジュールを共有できないための意図的な複製で、`README.md` にも「ロック形式を修正する場合は両アプリとランナーを同じ変更で検証する」と注記がある。

**影響**　ドリフトした場合の失敗モードが「ロックを取ったつもりで取れていない」＝ CSV / SQLite の同時書込みであり、静かに壊れる種類の事故になる。注記は人の記憶に依存する。

**推奨対応**　各リポジトリのテストに、当該ブロックの内容ハッシュを固定値と突き合わせる契約テストを1本置く（ハッシュだけなら他リポジトリのパスに依存しない）。書式を変える際はテストの期待値更新が3箇所同時に必要になり、取り違えを機械的に検出できる。

### P2-03［P2］設計書に存在しない運用フラグと状態ファイルがある

**該当**　設計書 §4.1 構成ツリー・§4.1-1 実行モード表・§4.9 既存アプリ変更表。

**根拠**　実装に存在して設計書に記載がないもの: ランナーの `--test-weekly`（試験タスクで週次枠を再現する）、`--include-legacy-state`（復元セットに移行前の人間向け記録を含める）、子CLI側の `--ingest-run-dir` / `--business-from` / `--ingest-status` / `--ingest-evidence` / `--summary-proof`、状態ディレクトリの `verified-artifacts.json`（清掃台帳）と `cutover.json`（切替段階の記録）。`--business-from` は §4.4-1 (1) が「利用日下限の引数を追加する」と要求した実体だが、名前が本文に現れない。

**影響**　設計書は「実装済み」ステータスの正本であり、Phase 2 や障害対応でここを読む人が実際の入口を把握できない。`cutover.json` は切替可否の判定に使われるファイルなので、構成ツリーにないのは追跡上の欠落。

**推奨対応**　§4.1 ツリーに `verified-artifacts.json` と `cutover.json`、§4.1-1 に `--test-weekly` / `--include-legacy-state`、§4.9 の各ファイル行に実際の引数名を追記する。

### P3-01［P3］照合器が元メールのパーサを独立に再実装している

**該当**　`lib/verify.mjs`（`verifyTypeA` / `verifyTypeB` / `sellerItems` / `preorder`）。

**根拠**　適用前の金額照合を「本番パーサの結果を信用せず元メール本文から独立に再計算する」方式で実装しているため、商品行・数量・金額・総計・割引・予約注文の除外条件を `amazon-tracker/tools/gmail-fetch-local.mjs` とは別の正規表現で解釈している。照合としては正しい設計（§4.3-1a の要求どおり）だが、メール書式の追加・変更に対して**2箇所を同時に追随させないと、本番パーサが正しく読めた週に照合側が落ちる**。落ちた場合の結果は `permanent` で、人の解除が必要になる。

**推奨対応**　書式に関する変更を入れるときは `gmail-import-rules.md` のパースルールと照合器の両方を更新する、という運用メモをルール文書側に1行置く。可能なら同一の合成メールを両方に通して結果を突き合わせる回帰を1本追加する。

### P3-02［P3］未解決隔離の自動削除は実装上無効で、設計表の「30日保持」が効かない

**該当**　`lib/cleanup.mjs`（`autoCleanup` が `kind === 'isolation'` を常に残す）、設計書 §4.6-1 の保存期間表。

**根拠**　隔離 JSON のうち空配列のものだけ `empty_isolation`（7日）として自動削除され、内容のあるものは期限超過でも削除されない。設計表の「隔離 JSON は30日保持」は、未解決か解決済みかを機械判定できないため実質適用されない。保持側に倒しているので安全側の逸脱である。

**推奨対応**　設計表に「内容のある隔離は未解決とみなし自動削除しない（解決後は人が削除する）」と注記して実装に合わせる。

### P3-03［P3］`partial` は到達不能な結果値になっている

**該当**　設計書 §4.4-2 のジョブ結果表、`lib/state.mjs` の `OUTCOMES`。

**根拠**　カードを provider 単位のジョブへ分割した結果、「複数 provider のうち一部のみ成功」は provider ごとの `success` / 失敗として表現されるようになり、`partial` を設定する経路がなくなった。終了コードの集約には影響しない。

**推奨対応**　§4.4-2 に「Phase 1 では未使用（provider 単位の結果で表現する）」と注記する。

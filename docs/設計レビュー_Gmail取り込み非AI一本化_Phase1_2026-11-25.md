## 実装前に決める事項

### P1-01　カード取込は長期停止後に未取得期間を飛ばして成功する

**根拠と影響**　§1.2、§3.1、§4.3 は45日ルックバックで未実行分を回収できるとしている。カード側 `tools/lib/provider-config.mjs:95–104` は実行日から検索開始日を算出し、前回成功日は参照しない。11月25日を与えた実コードの検索開始日は3社とも10月11日だった。前回成功が9月26日なら、例えば10月1日着の対象メールは検索されず、3社すべて成功し得る。Amazon 側の検索状態を保っても回復しない。

**修正・受入**　カード側にも全3社の取込を確認済みの期間末を保持する。通常の45日窓でその翌日を覆えない場合は、欠けた期間を指定して取り込むか、期間を明示して成功扱いを保留する。初回移行では旧ログから確認済みの期間を特定する。既存の `--from` は検索開始と利用日の抽出下限の両方に作用するため、遅着通知も試験する（`tools/lib/parser.mjs:327–340`）。60日休止、途中の1社失敗、再実行の順で、古い対象明細が1回だけ残り、全期間・全社の確認後にのみ状態が進むこと。

### P1-02　Amazon の適用前検証から、注文総額と候補行の照合が抜ける

**根拠と影響**　§4.3（L230–234）は取得成功、失敗ファイルなし、`rows` が配列、という条件で apply に進む。現行の `amazon-tracker/gmail-import-rules.md:323–325` は、検索条件、型別通数・候補数、各行の型、複数商品の商品名・金額とメールの注文総額の照合も求める。`tools/gmail-fetch-local.mjs:560–578` の検査へ、注文総額1,000円を想定して300円×2行の合成候補を渡すと指摘は0件だった。これは候補検査の限界を示すもので、現行パーサが実メールで同じ誤りを起こした証拠ではない。CSVの28列検査だけでは金額差400円を発見できない。

**修正・受入**　取得結果と今回の元メッセージを照合する工程を apply の前に置く。予約除外後の型別通数、検索条件、商品行、注文単位の合計を確認する。適用後はバックアップ、実CSVの再読、隔離配列長と `isolated_amount_diff_only` の一致を確認してから開始日を進める。正常な複数商品、商品欠落、合計不一致、隔離記録不一致を用意し、適用前の異常ではCSVと開始日の双方が不変であること。

### P1-03　Windows で子CLIを起動し、JSONを受け取る契約が成立していない

**根拠と影響**　§4.1 は `spawn`、§4.2–4.3 は `npm run` と stdout JSON を指定する。Windows の一時ディレクトリにJSONを1件返す npm script を作り、既定の出力設定で照合した。シェルを介さない `npm` の起動は `ENOENT`、`cmd.exe` 経由の `npm run` は終了0でも npm の見出しが付き、stdout 全体の JSON 解析に失敗した。両アプリの `package.json` では対象3コマンドはいずれも Node スクリプトを直接実行している。実ジョブでは子がDBやCSVを更新した後に親だけが失敗扱いし、再試行する可能性がある。

**修正・受入**　例えば、各アプリを cwd として `process.execPath` に既存のエントリーファイルと引数配列を渡す。stdout を単一の JSON、stderr を診断用と定め、終了コードと必須項目を一緒に判定する。Amazon apply は `writeJson(stats)` で `validation` と `isolated_file` を同じ階層に出す（`tools/gmail-import-run.mjs:245–276,547–557`）。Windows実プロセスで正常・不正JSON・JSON付き非0終了を通し、空白を含むパスと限定した PATH でも動くこと。§8.1 の全子プロセスをスタブにする試験だけでは代替できない。

### P1-04　認証正本を渡しても別アカウントや別の出力先で成功し得る

**根拠と影響**　§4.2 の事前確認はプロフィールにメールアドレスがあることしか見ない。Amazon 側は3種類のアクセストークンと `GOOGLE_*` の値をファイルより優先する（`tools/gmail-fetch-local.mjs:9,111–118,587–596`）。カード側も独自のトークンと `GOOGLE_*` を優先する（`tools/lib/gmail-auth.mjs:30–34,84–99`）。アプリごとに異なる環境値を継承すると、Amazon の事前確認が成功しても2社の取得元が一致する保証はない。出力先にも `AMZ_GMAIL_IMPORT_ORDERS_CSV` と `CREDIT_CARD_DB_PATH` の上書きがある。別ファイルへ登録して本番用の検索状態を進める組合せが成立する。

**修正・受入**　ランナー起動時の子環境と本番出力先を定義し、認証・データパスの上書きを排除または検証する。正本の存在・構造、想定アカウントとの一致を値をログに残さず確認する。異なる合成資格情報を各優先環境変数に入れた場合、欠損正本と有効な環境トークンが同居する場合、別DB・CSVを指す場合を試す。後二者で本番用の成功状態が進まないこと。

### P1-05　親の終了後に残った書き手と再試行が競合する

**根拠と影響**　§4.5 のロックが追跡するのは親PID。子や孫が apply 中にタイムアウトした場合の停止確認、ロックの排他的作成・所有者確認、生存中かつ6時間超の優先規則がない。§4.8、§5 が残す旧Automation・直接CLIもこのロックを取らない。Amazon apply はCSVを読んでから一時ファイルを作り、バックアップ後に置換する（`tools/gmail-import-run.mjs:569–604`）。2件が同じ旧CSVを読めば、最後の置換で先行分が失われ得る。行単位の重複判定では同時書込みを防げない。

**修正・受入**　全書込み入口で排他を共有するか、切替中・手動保守中に他の入口を確実に止める。ロック取得を原子的にし、所有者だけが解放できるようにする。タイムアウト・強制終了時に書込みプロセスの停止を確認できるまで再試行を許さない。同時起動、親だけの異常終了、遅い子が残る場合、手動applyとの競合で、同一時点の書き手が1つ、CSV・バックアップに欠落がないこと。

### P1-06　切り戻すCSV・DBと検索開始日の時点が一致しない

**根拠と影響**　§7（L478）は新ランナーの最新開始日を旧Markdownに転記し、CSV・DBをバックアップから戻す。Amazon のバックアップは対象行を適用する直前のCSV（`tools/gmail-import-run.mjs:602–604`）。11月の成功後に10月のデータを戻して11月の開始日を転記すれば、間の注文は旧運用でも再取得されない。カード側もバックアップが45日窓より古ければ同じ問題が残る。

**修正・受入**　起動経路だけを戻す場合は確定済みデータを維持する。データ復元が必要な場合は、整合するCSV・SQLite・各検索期間を組にして復元し、旧新の実行を停止した状態で不足期間を再取込する。隔離環境で2週以上の成功後に古い世代へ切り戻し、再取込後に元の注文・取引の集合と金額が一致すること。

### P1-07　初回実行だけで履歴の一括削除を開始できる

**根拠と影響**　§4.6-2 は削除無効の本番実行→一覧確認→有効化の順だが、§6 #16 は通常の `node run.mjs`。削除許可を永続化する手順や、過去の本文を「適用済み」と判定する証拠がない。日付ディレクトリには取得成功・適用失敗も置ける。未解決隔離は保持するとしつつ、カードの実パス `quarantine/gmail-import` は §4.6-1 の許可ルート外。Amazon も同日の再試行成功で失敗マーカーを消す（`tools/gmail-fetch-local.mjs:649–655`）。日付とマーカーの有無から前回の適用成功は判定できない。§10-10 で過去の取得元を再構成する選択肢も残っている。

**修正・受入**　初期状態で削除を無効にし、取込受入と対象確認後に明示的に有効化する。現在の実行結果と過去分を区別し、適用成功を証明できない履歴・未解決隔離は保留する。対象をファイル種別・実ルート単位で列挙し、§10-10 の方針を一括削除前に決める。成功・失敗・状態不明・同日再実行・未解決隔離を混ぜた検体で、初回は削除0件、確認後の実削除は承認済みの集合と一致すること。

### P1-08　手動フォールバックと切り戻しでAIによる取得を再開する

**根拠と影響**　§9 は取得経路からのAI排除を受入条件とするが、§4.9・§5 は Claude の `/amazon-import` を残し、§7 は旧Codex Automation 2本の再有効化を指定する。現行の親 `.claude/commands/amazon-import.md:38–56,73` はMarkdownを読んで REST 取得CLIとapplyを動かし、旧状態を更新する。定期タスクの親プロセス1件を調べてもこの経路は検証できない。Google「Workspace AI Tools Addendum」項目1は、ツール自体がAIである場合に加え、AIによって駆動される場合も対象に含める（2026-11-25確認）。旧構成についての個別判断は未取得という正本の留保を踏まえても、自ら選んだ運用方針と矛盾する。

**修正・受入**　人が直接起動する復旧用入口と、AIが参照できる診断・サマリの範囲を明記する。親のコマンド本文、取込用スキル・旧Automationの実行指示、切戻し手順を対象に含め、手動復旧時も同じ状態と排他を使う。定期・手動・障害復旧・期限後の切戻しごとに、取得を指示する主体と参照・更新する状態を一覧にし、旧AI起動経路が有効にならないことを確認する。

## 外部仕様の訂正

§1.1 の日程表では「利用制限」を2月1日にまとめている。Google「Usage tiers and quotas for Google Workspace APIs and MCP servers」のロードマップ（2026-11-25確認）は、2027-02-01 のAI向けMCP要件と、2027-04-01 の全プロジェクトに対するStandard上限の適用・課金開始を区別する。また条件を満たす組織内利用には、一部REST APIのプロジェクト上限について例外申請経路がある。本件の例外適格性と実使用量は未確認。個別プロジェクトが上限内かどうかは §8.4 の実測で判断する。

## 判定を見直す条件

P1の8件について、正本の該当節・実装順・受入条件の三者が同じ動作を指し、担当者が例外時のデータ・検索状態・次回動作を一意に決められること。P2の5件は切替前の試験項目と期待結果まで正本に反映する。実装前の設計判定と、本番の週間運用を開始できるかの判定は別々に行う。

今回の検証は既存CLI、ルール、公開一次資料の照合と、合成候補・固定日付・Windows子プロセスによるオフライン確認まで。新ランナーは未実装であり、Gmail接続、実資格情報の再検証、本番CSV・DBへの取込、一括削除、Automation・タスクの切替は未試験。

## 1. 目的・背景

Google ドライブの同期作業領域にある別名により、`lib/env.mjs` の `verifiedPath` が書き込み先を拒否し、`lib/cleanup.mjs` の `identify` が過去分の候補から除外した。同期対象から外した後も、既存の別名は残る。現行の計画は除外の理由を表示しない。

## 2. スコープ

清掃計画のファイル検査と結果表示を修正する。運用では業務データ、ステージング、バックアップ、復元セットの配置を対象とする。

## 3. 設計・仕様

恒久対策は、運用中の業務データ・ステージング・保全資料を同期対象外に置き、両アプリ・ランナー・復元先が同じ扱いになるようにする。現在の配置が継続して同期対象外なら同じパスを使用できる。配下に同期が再設定される運用へ変更する場合は、事前に同期対象外の保存先と参照箇所を棚卸しし、同一時点の復元セットで切替と復元を確認する。別名の列挙後に作り替えられる余地とクラウドへの複製を残すため、既知の同期作業領域にも `nlink` の例外を設けない。

### 計画の診断

- `createCleanupPlan` は、走査中に清掃対象の種別と判定できたファイルを `identify` が拒否した場合、理由を記録する。理由は `multiple_hardlinks`、`not_regular_file`、`redirected_path`、`missing_file`。対象外の種別は件数に含めない。走査がもともと辿らないディレクトリとシンボリックリンクは走査範囲外。
- 非公開の計画に `excluded` を加え、`root`、対象の `path`、`kind`、`reason` を記録し、計画 ID に含める。これらの対象は従来の `entries` に入れず、承認と削除から除外する。`excluded` の無い旧計画も現行の検証手順で読み込める。
- `--cleanup-plan` の結果の `excluded` には、ルート・種別・理由ごとの件数だけを出す。対象の実パス・内容ハッシュ・注文やメールの識別子は標準出力・定常ログに出さない。出力先検査による終了コード4、定常清掃、承認時と実行直前の検査は現行どおり。

## 4. 受け入れ条件と検証

1. 合成ファイルのハードリンクで走査・除外理由・件数・計画からの除外を確認する。承認件数・実行対象への混入がないことと、CLI 出力にパスがないことを確認する。
2. 元ファイルの内容を保持したまま、所有者が承認した別名だけを作業領域内から取り除く。元ファイルのリンク数・サイズ・必要な場合は行数、および清掃計画の対象件数を照合する。未知の別名は処分せず作業を止める。
3. 運用配置を変える場合は、先に復元セットを同期対象外に保全し、CSV・SQLite・state の整合性と `nlink === 1` を確認してから切り替える。

## 5. リスク・注意点

切替が失敗した場合は取り込みを止め、同期対象外の確認済み構成に戻す。クラウド側に保存済みの複製は [Phase 1](修正設計書_Gmail取り込み非AI一本化_Phase1_2026-11-25.md) §4.6-3 で扱う。

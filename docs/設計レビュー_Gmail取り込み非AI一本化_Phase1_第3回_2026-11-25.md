## 実装前に解消する指摘（P1）

### R3-01［P1］既存CLIの変更範囲が §2.1・§6 と §4.9・§7 で矛盾している

**根拠と影響**　第2回レビューの反映により、既存CLIの変更は §2.1 IN の一覧表および §6 #14–18 で 5ファイルへ拡大された。一方、§4.9（既存2アプリ側の変更）では `credit-card-tracker` が「コード：変更なし」のままであり、`amazon-tracker` の表にも `tools/gmail-import-run.mjs`（CSV読込前ロック、置換行集計、保留）および `tools/gmail-fetch-local.mjs` の `account_fingerprint` 出力追加が記載されていない。また §7 リスク表の末尾にも「認証フォールバック削除とロック取得追加の3ファイルに限定」と旧記述が残っている。第2回追加レビューの条件（§2.2・§4.9・§6・§8・§9 の記載一致）を満たしておらず、実装時に参照箇所によって改修漏れが生じる。

**修正と受入**　§4.9 の `amazon-tracker` および `credit-card-tracker` の変更一覧表と §7 のファイル数記載を、§2.1 IN・§6 #14–18 の 5ファイルの内容と完全に一致させる。§2.1・§2.2・§4.9・§5・§6・§7 の間で変更対象ファイル数および各ファイルの変更要旨に齟齬がないことを確認する。

### R3-02［P1］「定常の自動削除（§4.6-1）」と「承認の1回消費（§4.6-2a）」が衝突している

**根拠と影響**　§4.6-1 は「今回の実行で生成したメール本文 JSONL は適用成功を確認した直後に削除」「候補 JSON 等は 7日保持後に削除」と定常の自動削除を定めている。しかし §4.6-2a では「承認は1回の削除実行で消費し、`state/cleanup-enabled` と計画台帳を削除する。継続して削除する場合は毎回新しい計画と承認を要する」と規定している。このまま実装すると、初回の一括削除後に `state/cleanup-enabled` が消滅し、毎週の無人定期実行で中間ファイルが一切自動削除されなくなる。

**修正と受入**　削除の承認・有効化を以下の2系統に明確に分離する。
1. **初回・過去分の一括削除（§4.6-2 / §4.6-2a）**: `plan_id` と対象ファイルのハッシュに束縛し、1回の実行で承認を消費する。
2. **定常の自動削除（§4.6-1）**: 初回一括削除の完了後（または明示的な定常有効化フラグ、例：`state/auto-cleanup-enabled` の配置後）は、「今回の実行で `gmail-ingest` 自身が生成し、適用成功を確認した成果物」およびその保持期限切れ分のみを定期実行時に自動削除する（過去分・未解決隔離・`parse-failures.json` を含むディレクトリは引き続き自動削除の対象外）。

受入は、初回一括削除の承認消費後に計画差し替えによる過去分削除が起きないことと、定常有効化後の週次実行で今回生成した本文 JSONL のみが適用成功後に自動削除されることの両方を確認する。

### R3-03［P1］確定失敗（`permanent`）時の停止粒度が §4.5 と §4.5-2 で衝突している

**根拠と影響**　§4.5-2 は「全体停止（認証・アカウント・出力先照合失敗、破損 state、`pending_human_review` ロック）」と「provider / ジョブ単位の停止（解析失敗・CSV検証失敗・照合不一致。他のジョブは通常どおり実行する）」を明確に区別している。一方で、§4.5 のリトライ節には「`run.mjs` は起動時に `last_outcome` を読み、直近が `permanent` で人の確認がない場合は再実行せず終了コード 5 で終わる」という旧記述が残っている。起動時に一律で終了コード 5 を返して終了すると、1社または1ジョブの確定失敗によって正常な別ジョブまで停止し続け、§4.5-2 および R2-14 の目的を損なう。

**修正と受入**　§4.5 の起動時判定を §4.5-2 に合わせて次のように統一する。
- 起動時に全体を一律停止するのは全体停止事由（終了コード 1 / 3 / 4）のみとする。
- 個別ジョブ・provider に未承認の `permanent` が残っている場合は、**その対象だけをスキップ**し、他の正常なジョブ・provider は通常どおり実行する。
- 全体終了コードの扱いを明記する。たとえば「実行対象すべてが未承認の `permanent` でスキップされた（新規に実行したジョブが 0件）」場合のみ終了コード 5 とし、他ジョブを実行して `transient` が発生した場合は終了コード 2 を返す（タスクスケジューラの 30分後再試行でも未承認 `permanent` は再実行せず `transient` 対象のみ再試行する）。

受入は、カード1社が未承認 `permanent` の状態で定期再起動した際、当該1社のみスキップされ、残りのカード2社および Amazon ジョブが正常に実行・更新されること、全対象が未承認 `permanent` の場合のみ終了コード 5 で即終了することを確認する。
